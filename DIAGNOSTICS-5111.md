## Diagnostic-only additions

- Main ES callback registers received AUTH metadata in a 4,096-entry bounded ledger. No ES pointers/paths/arguments retained. The real retained-message paths mark credential/prelaunch phases and worker/watchdog claims. Claiming never removes a record. Only a successful ES response return removes it; failed returns remain visible. Duplicate-attempt counting covers requests still pending, not attempts after a successful return removed the record. Capacity overflow is counted rather than evicting an unanswered request. Reused addresses have distinct kernel message-time keys.
- A dedicated diagnostics Thread (independent of GCD worker-pool availability) polls once/second and logs at most eight newly overdue records per tick after half the kernel message-to-deadline window. Logs contain event type, phase, ages, deadline and attempts, not user paths. Diagnostics cannot execute while the process is suspended and do not observe messages not yet delivered. The ledger does not change replies, fallback policy, ES caching or watchdog scheduling.
- The actual retained-response ownership primitive is exercised under a race. Unit tests also cover failed response returns, claimed-but-pending work, phase coverage and capacity. These are not an exhaustive fake-ES replay of every handler branch and do not establish all branches reply correctly.
- Passive task counters sample physical footprint, resident/virtual memory and thread count at one-second cadence, retaining scalar peaks only. Scan counters expose active/completed scans and streaming SHA byte totals. USB progress is published every 256 enumerated entries and on completion, with at most 32 run records. No autorelease, scan-cap, duplicate-mount or scanning-policy fix is included.
- A dedicated utility queue inspects /Library/Logs/DiagnosticReports once/minute. It reads only regular no-follow NickExtension IPS files, <=8 MiB/file and <=16 MiB of new data/pass, with at most 512 directory entries and 128 parse-cache entries. JSON is inert data. Only exact Nick bundle ID and ENDPOINTSECURITY code 2 match. Incident UUIDs deduplicate reports. Count scope is available reports, not an authoritative historical count of all kills. Partial/unavailable inspection remains explicit, not a false zero-kill claim.
- A previous-session attribution requires PID/build agreement, launch time within 120 seconds of health initialization, and capture near its last heartbeat. Same-boot transitions are overridden only by a positive match. A missing, delayed, unreadable or unmatched report leaves the cause unknown. Broad directory inspection can be partial and needs installed validation.

## Private build and allocation logging

The private archive uses NICK_PRIVATE_DIAGNOSTICS via an external build xcconfig, adding Diagnostic to visible version labels without changing numeric version/build values. Package is local only, not merged, pushed, added to an appcast or website.

Scripts/diagnostics/prepare-allocation-logging.py defaults to validation/command preview for an explicit, root-owned and correctly signed Nick System Extension launchd service. Explicit --enable-next-launch requests only a service-specific next-launch environment override. It never attaches, restarts, uses global setenv, changes entitlements or disables SIP. Launchd may reject it. Activation and a bounded collection procedure MUST be verified locally before reporter use. The helper itself does not bound allocator log disk growth; do not enable it until that separate procedure exists. No allocation logging has been enabled or claimed functional here. Presence of the environment variable in health is not proof of activation.
